## 3. 데이터 모델 설계

### 3.1 자료구조 선택 이유

프롬프트 데이터는 **리스트(list) 안에 딕셔너리(dict)를 담는 구조**로 설계했다.

| 후보 구조 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| 리스트 + 딕셔너리 | 필드에 이름으로 접근 가능해 가독성이 좋음, 순서를 유지하며 순회 가능, 필터링/검색을 리스트 컴프리헨션으로 간단히 구현 가능 | ID로 직접 접근 시 O(n) 탐색 필요 | ✅ 채택 |
| ID를 key로 하는 딕셔너리(`{id: {...}}`) | ID 기반 조회가 O(1) | 목록 순서 보장이 약하고, 순번 출력 시 추가 정렬 필요 | ❌ 미채택 |
| 클래스(예: `Prompt`) 인스턴스 | 타입 안정성, 메서드로 로직 응집 가능 | 미션 범위(기초 문법) 대비 과한 설계, 학습 목표(리스트·딕셔너리 다루기)와 어긋남 | ❌ 미채택 |

현재 데이터 규모(프롬프트 수백 개 이하)에서는 O(n) 탐색 비용이 무시할 수준이고,
목록 출력이 가장 빈번한 동작이므로 순서 유지가 되는 리스트 구조가 더 적합하다고
판단했다.

### 3.2 필드 정의

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | int | `get_next_id()`로 자동 발급, 기존 최대값 + 1 |
| `title` | str | 필수, 빈 값 불가 |
| `content` | str | 필수, 빈 값 불가 |

| `usage_count` | int | 상세 보기 조회 시마다 1씩 증가 (보너스 2), 기본값 0 |

## 4. 주요 기능 및 정책

### 4.1 메뉴 (`show_menu`)
```
1. 프롬프트 목록 보기
2. 프롬프트 추가
3. 카테고리별 조회
4. 키워드 검색
5. 프롬프트 상세 보기 (조회수 증가)
6. 즐겨찾기 관리
7. 프롬프트 수정/삭제
8. 인기 프롬프트 (조회수 Top N)
9. Markdown 파일로 내보내기
0. 프로그램 종료
```
숫자가 아니거나 목록에 없는 번호를 입력하면 `main()`의 else 분기에서
"잘못된 번호입니다" 안내 후 메뉴를 다시 표시한다.

### 4.2 프롬프트 추가 (`add_prompt`)
- 제목/내용은 빈 문자열이면 `while` 루프로 재입력을 요구한다 (필수 검증).
- 카테고리는 미입력 시 `"기타"`로 자동 지정한다.
- 추가 완료 시 `save_prompts(prompts)`를 즉시 호출해 JSON 파일에 반영한다.
- **동명(제목 중복) 처리 정책**: 제목 중복을 별도로 검사하지 않고 모두 새
  ID로 등록한다. 동일한 프롬프트를 다른 버전/카테고리로 저장하고 싶은
  경우를 허용하기 위한 의도적 설계이며, ID가 사용자 관점의 고유 식별자
  역할을 한다.

### 4.3 카테고리별 조회 (`show_by_category`)
- 카테고리 목록은 고정 리스트가 아니라 현재 `prompts`에 실제로 존재하는
  값을 `set()`으로 중복 제거해 동적으로 생성한다.
- **매칭 규칙**: 번호 입력 시 인덱스로 정확히 매칭하고, 이름을 직접 입력한
  경우는 **완전 일치(대소문자 구분)** 로 비교한다. 카테고리는 자유 입력
  필드이므로 느슨한 매칭을 허용하면 오탈자(예: "텍스트생성" vs "텍스트
  생성")를 서로 다른 카테고리로 방치하게 되는 문제를 피하기 위함이다.

### 4.4 키워드 검색 (`search_prompt`)
- 제목·내용 양쪽에서 `lower()`로 변환해 **대소문자 무시 부분 문자열 검색**을 수행한다.
- **정렬/페이징 정책**: 검색 결과는 별도 정렬 없이 `prompts` 리스트 등록
  순서(ID 오름차순)를 그대로 유지해 출력한다. 페이징은 적용하지 않았다.

### 4.5 상세 보기 (`show_prompt_detail`) — 보너스 2: 조회수 기록
ID로 프롬프트를 찾아 제목/카테고리/즐겨찾기/**조회수**/내용 전체를 출력한다.
조회할 때마다 `usage_count`를 1 증가시키고 `save_prompts(prompts)`로 즉시
저장한다. 숫자가 아닌 입력과 존재하지 않는 ID는 각각 구분해 안내한다.

### 4.6 즐겨찾기 관리 (`manage_favorites`)
서브 메뉴로 "모아보기"와 "추가/해제"를 분리했다. 추가/해제는
`is_favorite = not is_favorite` 토글 방식이며, 변경 즉시 `save_prompts`를
호출해 파일에 반영한다.

### 4.7 프롬프트 수정/삭제 (`edit_or_delete_prompt`) — 보너스 2
하나의 함수 안에서 서브 메뉴(①수정 ②삭제)로 분기한다.
- **수정**: 제목/내용/카테고리 각각 빈 입력이면 기존 값을 유지하고,
  값이 있으면 해당 필드만 교체한다. 필드 단위로 "변경할 것만 골라
  입력"하는 방식이라 실수로 다른 필드를 지우는 것을 방지한다.
- **삭제**: `y/n` 확인 절차를 거친 뒤 `list.remove()`로 제거한다.
  확인 없이 즉시 삭제되지 않도록 해 오조작을 방지했다.
- 두 작업 모두 완료 즉시 `save_prompts(prompts)`로 저장한다.

### 4.8 인기 프롬프트 Top N (`show_top_prompts`) — 보너스 2
`usage_count` 기준 내림차순으로 정렬(`sorted(..., reverse=True)`)해 상위
N개를 출력한다. N은 사용자가 직접 입력하며, 숫자가 아니거나 0 이하면
기본값 5를 사용한다.

### 4.9 입력 유효성 기준 요약

| 필드 | 검증 규칙 |
|---|---|
| 제목 | 빈 문자열 불가, 재입력 요구 |
| 내용 | 빈 문자열 불가, 재입력 요구 |
| 카테고리 | 빈 값이면 "기타"로 자동 대체 (재입력 요구 안 함) |
| ID 입력(상세보기/즐겨찾기/수정삭제) | 숫자가 아니면 즉시 오류 안내 후 함수 종료 (재입력 루프 없음) |
| Top N 개수 | 숫자가 아니거나 0 이하면 기본값 5로 대체 |

### 4.10 종료 시 동작
`0`을 입력하면 종료 메시지를 출력하고 `main()`의 `while` 루프를 `break`로
빠져나간다. 모든 변경 사항은 발생 시점마다 이미 JSON 파일에 저장되어
있으므로, 종료 시 별도의 저장 작업은 필요하지 않다.

## 5. 보너스 과제 구현 내용

### 5.1 보너스 1 — 프롬프트 영속화 및 내보내기

**JSON 저장/불러오기**
- `save_prompts(prompts_data)`: `json.dump(..., ensure_ascii=False, indent=4)`로
  `prompts.json`에 저장한다. `ensure_ascii=False`로 한글이 유니코드 escape가
  아닌 읽을 수 있는 형태로 저장되도록 했다.
- `load_prompts()`: 프로그램 시작 시 호출된다. `prompts.json`이 있으면
  불러오고, 없으면 `default_prompts`(기본 3개 데이터)를 저장까지 한 뒤
  반환해 다음 실행부터는 파일 기반으로 동작하게 한다.
- **저장 시점 정책 — write-through(즉시 저장) 방식 채택**: 메뉴에 별도의
  "저장" 항목을 두지 않고, 추가/수정/삭제/즐겨찾기 토글/조회(사용 횟수 증가)
  등 **데이터를 변경하는 모든 동작 직후 자동으로 `save_prompts()`를 호출**
  하도록 설계했다.
  - 장점: 사용자가 저장을 깜빡해 변경 사항을 잃어버릴 위험이 없고, 프로그램이
    비정상 종료되어도 마지막 변경 시점까지는 파일에 반영되어 있다.
  - 단점: 변경마다 파일 I/O가 발생해 데이터가 매우 많아지면 저장 메뉴를
    따로 두는 방식보다 느릴 수 있다. 다만 콘솔 프로그램 특성상 변경 빈도와
    데이터 규모가 크지 않아 이 트레이드오프는 무시할 수준이라 판단했다.
- **하위 호환 처리**: 이전에 저장된 JSON 파일에 `usage_count` 필드가 없는
  경우(예: 보너스 기능 추가 이전 버전으로 저장된 파일)를 대비해,
  `load_prompts()`에서 각 항목에 `usage_count`가 없으면 0으로 채워 넣는다.
  필드가 없어 발생하는 `KeyError`를 방지하기 위한 방어적 설계다.

**Markdown 내보내기**
- `export_to_markdown()`: 파일명을 직접 입력받되(미입력 시
  `prompts_export.md`), 확장자 `.md`가 없으면 자동으로 붙인다.
- **파일 구성 방식**: 카테고리마다 별도 파일을 만드는 대신, **파일 하나
  안에서 카테고리별로 `##` 섹션을 나누는 방식**을 택했다. 카테고리 수가
  늘어나도 내보낸 결과물을 파일 하나로 공유·열람하기 쉽고, 문서 전체를
  훑어보기에도 더 편하다고 판단했기 때문이다.
- 각 프롬프트는 제목(`###`, 즐겨찾기 시 ⭐ 표시), 조회수, 내용을 코드
  블록(```text)으로 감싸 원문 그대로 보이도록 출력한다.

### 5.2 보너스 2 — CRUD 및 사용 기록

| 요구사항 | 구현 함수 | 비고 |
|---|---|---|
| 프롬프트 수정 | `edit_or_delete_prompt()` (선택 1) | 필드별 선택적 수정 |
| 프롬프트 삭제 | `edit_or_delete_prompt()` (선택 2) | y/n 확인 절차 포함 |
| 조회수(사용 횟수) 기록 | `show_prompt_detail()` | 상세 보기 시 `usage_count` +1 |

## 6. 코드 구조

```
load_prompts()            # JSON 파일에서 데이터 로드 (없으면 기본 데이터 저장 후 반환)
save_prompts()             # 현재 데이터를 JSON 파일로 저장
get_next_id()              # ID 자동 생성 (기존 최대값 + 1)
show_menu()                 # 메뉴 출력 및 번호 입력 받기
show_prompt_list()          # 목록 출력 (여러 기능에서 공통 재사용)
add_prompt()                 # 프롬프트 추가
show_by_category()          # 카테고리별 조회
search_prompt()              # 키워드 검색
show_prompt_detail()        # 상세 보기 + 조회수 기록
manage_favorites()          # 즐겨찾기 관리 (모아보기 + 토글)
edit_or_delete_prompt()     # 프롬프트 수정/삭제
show_top_prompts()          # 조회수 Top N 목록
export_to_markdown()        # Markdown 파일로 내보내기
main()                        # 메뉴 루프 제어
```

`show_prompt_list()`를 전체 목록/카테고리별 조회/검색 결과/즐겨찾기 목록에서
공통으로 재사용해 코드 중복을 줄인 것이 핵심 설계 포인트다. 데이터 변경이
일어나는 함수(`add_prompt`, `show_prompt_detail`, `manage_favorites`,
`edit_or_delete_prompt`)는 모두 작업 마지막에 `save_prompts(prompts)`를
호출해 영속화 로직을 각 함수가 직접 책임지도록 했다.

## 7. Git / GitHub 작업 내역

### 7.1 커밋 메시지 컨벤션
기능 단위로 아래와 같은 접두사 규칙을 사용해 커밋했다.

| 접두사 | 의미 | 예시 |
|---|---|---|
| `feat:` | 새 기능 추가 | `feat: 프롬프트 JSON 저장/불러오기 기능 구현` |
| `fix:` | 버그/예외 수정 | `fix: 빈 제목 입력 시 재요청 로직 추가` |
| `docs:` | 문서 변경 | `docs: README 실행 방법 추가` |
| `chore:` | 설정/기타 작업 | `chore: .gitignore 추가` |

### 7.2 브랜치 전략
- 네이밍 규칙: `feature/기능이름` (예: `feature/persistence`)
- 분리 기준: 메뉴 항목 하나(=함수 하나)가 새로 추가되는 작업 단위마다
  별도 브랜치를 생성했다. 단순 오탈자 수정이나 문서 변경은 `main`에서
  바로 커밋했다.
- 실제 병합 내역: `[ 예: feature/persistence 브랜치에서 JSON 저장/불러오기,
  Markdown 내보내기, 수정/삭제, 조회수 Top N 기능을 각각 커밋한 뒤
  git checkout main && git merge feature/persistence 로 병합 ]`

### 7.3 실행 명령 이력 (체크리스트)

| 작업 | 명령어 | 실행 여부 |
|---|---|---|
| 저장소 초기화 | `git init` | `[ ✅/⬜ ]` |
| 스테이징 | `git add` | `[ ✅/⬜ ]` |

## 9. 배운 점 및 회고

- 리스트+딕셔너리 구조와 ID key 딕셔너리, 클래스 구조를 비교해보며 데이터
  규모와 접근 패턴(순회 위주 vs ID 조회 위주)에 따라 적합한 자료구조가
  달라진다는 것을 이해했다.
- `show_prompt_list()`를 여러 기능에서 재사용하도록 설계하면서, 함수를
  나눌 때 "입력값을 다르게 받되 같은 출력 로직을 쓰는 부분"을 분리하는
  감각을 익혔다.
- 영속화 기능을 구현하면서 "언제 저장할 것인가"라는 설계 선택지가
  있다는 것을 알게 되었다. 메뉴로 저장 시점을 따로 두는 방식과, 변경할
  때마다 즉시 저장하는 방식(write-through) 중 데이터 유실 위험을 줄이는
  후자를 선택했고, 그 대신 파일 I/O 빈도가 늘어나는 트레이드오프를
  감수했다.
- 이전 버전 데이터(필드가 적은 JSON)를 새 버전 코드로 불러올 때 필드
  누락으로 오류가 날 수 있다는 것을 겪으며, `usage_count`가 없으면
  기본값을 채워 넣는 하위 호환 처리의 필요성을 체감했다.
- Git 커밋 메시지 컨벤션과 브랜치 네이밍 규칙을 미리 정해두고 작업하니,
  나중에 `git log`만 봐도 무슨 작업을 했는지 파악하기 쉬웠다.
